## Gestion de Peticiones:
- **Disparar peticiones HTTP de forma constante** y bombardear de peticiones HTTP al **backend suele ser una mala practica**, por ende las peticiones HTTP se suelen guardar en algun tipo de cache, ya sea en memoria o en algun otro lado.
- El problema viene cuando queremos mantener ese cache actualizado, por si en el backend agregan o cambian algun otro dato. Asi que suelen aplicar diferentes estrategias de que tanto cambien los datos.

### Estrategias de Actualizacion de cache:

 > ⚠️ *Antes que nada, es importante saber que se debe tomar una u otra estrategia dependiendo de que tan cambiantes sean los datos.*



Guardar los datos de la API en el store puede hacer que, si los datos cambian en el backend y no se hace un refetch, la app muestre datos desactualizados. Así se maneja este problema en Angular y en TanStack Query:

---

## *En Angular (con store propio):*

- *Por defecto*, los datos en el store se mantienen igual hasta que tú decidas actualizarlos (por ejemplo, tras una mutation o con un botón de recarga).
- *Soluciones comunes:*
  1. *Refetch manual:*  
     Después de una mutation (POST, PUT, DELETE), vuelves a pedir los datos al backend y actualizas el store.
  2. *Refetch automático:*  
     Puedes programar recargas periódicas (polling) o recargar cuando el usuario vuelve a la vista.
  3. *WebSockets/Eventos:*  
     Si necesitas datos en tiempo real, puedes actualizar el store cuando recibes eventos del backend.
  4. *Optimistic update:*  
     Actualizas el store localmente antes de que el backend confirme el cambio, y haces rollback si falla.

- *Resumen:*  
  En Angular, tú controlas cuándo y cómo se actualiza el store. Si no haces refetch, los datos pueden quedar desactualizados.

---

## *En TanStack Query:*

- *Caché reactiva y controlada:*  
  TanStack Query guarda los datos en caché, pero tiene mecanismos automáticos para mantenerlos frescos:
  1. *Stale time:*  
     Puedes definir cuánto tiempo los datos se consideran “frescos”. Cuando se vuelven “stale”, TanStack puede hacer un refetch automáticamente.
  2. *Refetch on window focus:*  
     Por defecto, cuando el usuario vuelve a la pestaña, TanStack puede volver a pedir los datos.
  3. *Invalidación tras mutation:*  
     Cuando haces una mutation, puedes invalidar la query relacionada y TanStack hará un refetch automático.
  4. *Refetch manual:*  
     Puedes forzar un refetch en cualquier momento.

- *Resumen:*  
  TanStack Query automatiza la actualización de los datos y te da control granular para mantener la UI sincronizada con el backend, minimizando el riesgo de datos desactualizados.
